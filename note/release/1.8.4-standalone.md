## 改动（性能，行为不变）

### R1：机器配方匹配热路径（SF-id 预筛 + 纯-SF 机器闸门）
- **问题**：`WTRecipeMachine.findMatch` 在机器输出占满 / 持不匹配输入时每 tick（10Hz）全量扫描配方，
  每次比较调 `SlimefunUtils.isItemSimilar`，其在类型匹配后调 `SlimefunItem.getByItem()` 两次。对 SF 头颅类
  机器（材质同为 PLAYER_HEAD、仅 SF id 不同），**每条配方比较都付此代价**。
- **优化**：
  1. `WTRecipe.inputSfId(i)`（惰性、非游离）：预解析每个输入的 SF id。
  2. `WTRecipeMachine.findMatch`：每 tick 预解析各输入槽 SF id 一次（读 PDC），用廉价必要条件
     `idCertainlyMismatch`（两端均 SF 且 id 不同）跳过确定不匹配者，省去昂贵的 `isItemSimilar`。
  3. **机器级闸门 `sfPrune`**：仅纯-SF 机器（≥2 配方且所有输入为 SF 物品）启用；否则逐字回退原算法（零回归）。
- **基准收益**（`benchmark/`）：纯-SF 机器 `isItemSimilar` 调用数 O(配方数)→O(命中数)，耗时 **7.5~26×**；
  原/混合机器 **1.00×（零回归）**。
- **生产闸门映射**：闸门 ON（受益）= WT_ZHONGZIJDY/WT_NGZHONGZIJDY/WT_HWSCPCLJ/WT_XIELONG/WT_CHANLUANSHI/WT_TUZAIJI；
  其余 off（零回归）。

## 安全性 / 保真度（红线）
- 仅在「两端均 SF 且 id 不同」时跳过 `isItemSimilar`——此情形其 both-SF 分支必返回 false，**不改变匹配结果**；
  其余情形仍交 `isItemSimilar` 定夺，完整保留 RSC first-match/distinct 语义与 DistinctiveItem/meta 边界。
- `stillValid` 复校、逐条 try/catch 故障隔离等既有数据安全防护均不变。
- 非-SF 机器代码路径逐字不变（闸门关闭）。
